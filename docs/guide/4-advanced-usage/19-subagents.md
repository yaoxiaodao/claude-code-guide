# 第十九章：Subagents 与并行会话

::: tip 学习目标
学完这章，你会用内置子代理省上下文、写出第一个自定义 subagent，并知道什么时候该用分叉、后台会话或 worktree。
:::

::: warning 别和"权限模式"搞混
- **权限模式**（第十七章）管的是"它能不能不问你就动手"
- **Subagent** 管的是"派一个独立的助手去干一件事，只在结束时把结论带回来"

两者完全无关，不要混为一谈。
:::

## 一句话说清它解决什么问题

你让它"在整个项目里找出所有写死的超时时间"。它要 `grep` 几十个文件、读十几个结果——这些搜索结果会**全部留在你的主对话里**，占掉上下文，而你在拿到答案后再也不会看它们第二眼。

Subagent 的做法：把这件事扔进一个独立的上下文窗口，干完只回一句"在 7 个文件里找到 12 处，都在 `src/api/` 下，清单如下"。**过程中的噪音不进入你的主对话**。

## 你其实已经在用它了

Claude Code 自带几个内置子代理，Claude 会自己判断何时用：

| 内置 subagent | 干什么 | 特点 |
|---|---|---|
| **Explore** | 搜代码、找文件、摸清项目结构 | 只读，不加载 `CLAUDE.md`，快 |
| **Plan** | 在做计划前收集上下文 | 只读，只在计划模式里用 |

所以你看到对话里冒出 `Explore(Find timeout constants)` 这样的行，就是它在派子代理。

## 什么时候派子代理，什么时候自己聊

| 用主对话 | 用 subagent |
|---|---|
| 需要来回商量、反复微调 | 任务自成一体，只要一个结论 |
| 各阶段共享大量上下文（规划→实现→测试） | 中间过程会产出大量你不需要的日志/搜索结果 |
| 改动很小、就几行 | 想限制它能用的工具（比如只读） |
| 慢一点没关系但要快反馈 | 想并行推进多条线 |

::: tip 经验值
**"这会读很多文件/输出很长，但我只想要结论"** —— 出现这个念头时就该派子代理。
:::

## 写第一个自定义 subagent

Subagent 就是一个带 YAML frontmatter 的 Markdown 文件。最简单的做法：直接让 Claude 帮你写。

```
在 ~/.claude/agents/ 里创建一个叫 code-improver 的个人子代理，
扫描文件并给出可读性、性能、最佳实践三方面的改进建议。
它应该是只读的，用 sonnet 模型。
```

它会生成类似这样的文件：

```markdown
---
name: code-improver
description: 扫描文件并给出可读性、性能、最佳实践方面的改进建议。在写完或修改代码后使用。
tools: Read, Grep, Glob
model: sonnet
---

你是一个代码改进专家。对每个问题，先解释问题，再展示当前代码，
再给出改进后的版本。
```

三个字段最关键：

| 字段 | 作用 |
|---|---|
| `name` | 调用时用的名字 |
| `description` | **Claude 靠它判断什么时候该派这个代理**，写清楚触发场景 |
| `tools` | 限定它能做什么。只想要建议就只给 `Read, Grep, Glob` |
| `model` | 可以指定 `haiku` 这类便宜模型，省钱 |

### 放哪：项目级还是个人级

| 位置 | 生效范围 | 适合 |
|---|---|---|
| `.claude/agents/` | 当前项目，可提交到 git 与团队共享 | 团队约定的审查者、测试跑手 |
| `~/.claude/agents/` | 你机器上所有项目 | 个人习惯的工具 |

::: warning 常见坑
如果 `~/.claude/agents/` 这个目录是在会话开始**之后**才创建的，当前会话检测不到。重启 `claude` 就好。
:::

## 怎么调用

**方式一：自然语言**（Claude 自己决定派不派）

```
用 code-improver 子代理看看这个项目哪里能改进
```

**方式二：`@` 点名**（强制派它）

```
@"code-reviewer (agent)" 看一下我最近的认证改动
```

**方式三：整个会话以某个子代理身份运行**

```bash
claude --agent code-reviewer
```

## 前台还是后台

从主对话派出的子代理**默认在后台跑**，你可以继续干别的。它需要权限时，提示会冒到你的主会话里，标明是哪个子代理在请求。

想让它跑在前台、等它结束（比如你就是要它的结论才能继续），可以直接说"等它完成再继续"，或者关掉 fork 模式：

```json
// settings.json
{ "env": { "CLAUDE_CODE_FORK_SUBAGENT": "0" } }
```

## 分叉：带着当前上下文派活

普通子代理是**从零开始**的，它不知道你们前面聊了什么。每派一次都要重新解释背景，很浪费。

`/subtask` 是"分叉"：它继承当前完整对话，等于从你现在的状态复制出一个自己，去干一件旁支的活，干完把结果交回来。

```
/subtask 先把刚才那些改动的单元测试写出来，我这边继续改实现
```

它会在输入框下方的面板里跑，你继续干活，不打架。同一个起点还能分多个叉去试不同方案。

::: tip 一个判断
**"这事需要它知道我们刚才的讨论"** → 用 `/subtask`；**"这事从头讲得清楚"** → 用普通子代理。
:::

## 更重的手段：并行会话与 worktree

当你要同时推进几条**互不相干的线**，子代理就不够了，得上多会话。

| 手段 | 是什么 | 什么时候用 |
|---|---|---|
| `/background` | 把当前会话分离到后台，释放终端 | 一个长任务，你想先干别的 |
| `claude agents` | 一个屏幕看所有后台会话在干什么 | 同时开了好几个会话 |
| `/fork` | 复制当前会话到新的后台会话 | 想从同一处出发试两条路 |
| git worktree | 每个会话一个独立工作目录，改动互不干扰 | 同一仓库并行改代码，**必用** |

```bash
claude --worktree feature-a    # 在独立 worktree 里开会话
```

::: warning 没有 worktree 就别并行改同一个仓库
两个会话在同一个目录里改文件，会互相覆盖，且很难查。并行改代码一定配 worktree。
:::

## 成本与上下文提醒

- 子代理的请求**计入你的用量**，和主对话同一份额度
- 每个 subagent 的 `description` 会在启动时加载进上下文。所有子代理描述加起来超过 15000 token 会报警告——所以描述写简短，细节放进正文
- 子代理可以再派子代理，但最多三层

## 常见问题

**Q: Claude 不派我建好的子代理？**

A: 九成是 `description` 写得太含糊。改成"在什么情况下用它"的具体描述，比如「在完成一个功能、准备提交前使用」，而不是「一个代码审查者」。

**Q: 子代理卡在权限提示上？**

A: 它的提示会转到主会话里显示。看到就批，或者给它设只读工具集避免这类请求。

**Q: 子代理和 Skill 该选哪个？**

A: Skill 是**写好的提示词/流程**，在主对话里跑；Subagent 是**独立的执行单元**，在自己的上下文里跑并只回结论。要隔离噪音选 subagent，要复用话术选 skill（第十四章）。

## 练习题

1. 让它做一件"会读很多文件"的活，观察对话里出现的子代理调用行
2. 用自然语言让 Claude 帮你创建一个只读的 `doc-checker` 子代理
3. 用 `/subtask` 派一个旁支任务，主对话继续干别的
4. 用 `claude --worktree test-a` 在独立目录里开一个会话，`git worktree list` 看看它建了什么
