# 第九章：代码审查和优化

::: tip 学习目标
学完这章，你会用 Claude Code 进行高效的代码审查，发现潜在问题并给出优化建议。
:::

## 为什么 Claude 擅长代码审查？

传统代码审查依赖人工 Reviewer，受限于：
- 疲劳感 — 看了 50 个 PR 后注意力下降
- 上下文切换 — 打断手头工作去 Review
- 视角单一 — 一个人难免有盲点

Claude Code 做代码审查的优势：
- 不知疲倦，保持一致的审查标准
- 一次性覆盖安全、性能、可读性、逻辑多个维度
- 随时可用，不打扰你的工作节奏

## 开始代码审查

### 方法一：`/code-review`（最简单）

```
/code-review
```

它审查你**当前分支的改动**（未提交和已提交的 diff 都算），重点找正确性 bug，顺带看清理机会。

常用参数：

| 写法 | 作用 |
|---|---|
| `/code-review --fix` | 发现问题后直接改 |
| `/code-review high` | 指定审查强度（`low` / `medium` / `high` / `xhigh` / `max`） |
| `/code-review ultra` | 云端多代理深度审查，最彻底但慢 |
| `/code-review 1234` | 审查编号 1234 的 PR |
| `/security-review` | 只看安全漏洞 |

::: tip 老名字还能用
`/review` 现在是 `/code-review` 的别名，写哪个都行。新文章里统一用 `/code-review`。
:::

### 方法二：指定审查重点

```
/code-review
重点关注：安全漏洞和潜在的 SQL 注入
```

```
/code-review --fix
只检查性能问题，特别是循环和数据库查询
```

### 方法三：直接问具体问题

```
这个文件有没有安全风险？
```

```
帮我检查 auth.ts 中的密码处理逻辑是否安全
```

::: tip 先 `/diff` 再 `/code-review`
想先看它到底改了什么，用 `/diff` 打开实时差异面板。确认改动范围合理后，再跑审查。
:::

## 按类型分类的审查 Prompt

### 安全漏洞

```
审查这段代码的安全问题：
- SQL 注入
- XSS 攻击
- 密码明文存储
- 敏感信息泄露
- 不安全的依赖

【粘贴代码】
```

### 性能问题

```
分析这段代码的性能瓶颈：
- 循环效率
- 数据库查询（N+1 问题）
- 不必要的重复计算
- 内存占用

【粘贴代码】
```

### 代码可读性

```
审查这段代码的可读性：
- 变量命名是否清晰
- 函数是否过长
- 注释是否充分
- 是否有重复代码

【粘贴代码】
```

### 逻辑错误

```
审查这段代码的业务逻辑：
- 边界条件是否处理
- 异常流程是否覆盖
- 状态转换是否正确

【粘贴代码】
```

## 让 Claude 逐个修复

不要一次接受所有修改建议。逐个来：

```
先修复命名问题，其他的先不动
```

```
接下来处理安全漏洞
```

这样你可以控制改动范围，每步都可以 Review。

## 常见问题

**Q: Claude 说的对不对？**

A: 保持批判思维。Claude 的建议是基于模式识别，不一定理解你的业务逻辑。重要的改动先理解再接受。

**Q: 优化建议太多了？**

A: 正常。先处理高风险问题（安全 > bug > 性能 > 可读性）。用"先修复 X，其他的先不动"来控制范围。

**Q: 可以让 Claude 审查特定文件吗？**

A: 当然。直接说：`审查 src/auth/login.ts`

## 练习题

1. 用 `/code-review` 审查你项目中的任意文件
2. 让 Claude 重点检查安全漏洞
3. 用分步方式：先问"有没有 SQL 注入风险"，再问"有没有 XSS 风险"
